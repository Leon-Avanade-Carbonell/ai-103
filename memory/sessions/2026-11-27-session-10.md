### Ordinary lesson checks

1. **Prompt:** 'Tutor example: you have saved responses from prompt v1 and prompt v2 for the same 100 questions. You want to compare them using unchanged intent-resolution and groundedness criteria. Would you create two evaluation definitions, or reuse one definition for two runs? Why?'

   **Initial learner response:** 'Just one evaluation definitions, because only the processing (agent) needs to change. Evaluation should be the same for both agents'

   **Feedback:** Correct reusable definition. The tutor refined the distinction: agent responses are generated beforehand and evaluation scores saved outputs, not agent execution. No follow-up reported.

2. **Initial prompt:** 'a refund dataset contains Question, Answer, and ExpectedAnswer, but no policy text. Someone maps ExpectedAnswer to the groundedness evaluator’s context. Would that test whether the response is supported by the refund policy? What would you change?'

   **Initial learner response:** 'The question seems vague. Can you either rephrase your question or change it?'

   **Feedback:** This is prompt-quality feedback, not an incorrect content answer.

   **Rephrased prompt:** 'Question: Can I get a refund after 35 days? Answer: Yes, refunds are available for 60 days. ExpectedAnswer: No, this purchase is outside the refund window. Policy text: missing from the dataset. We want to check whether the agent’s answer is supported by the actual refund policy, not merely whether it matches an expected answer. What information would you add to the dataset and pass as the groundedness evaluator’s context?'

   **Learner response:** 'Maybe change the mapping to match other options for groundedness, or change the evauation.'

   **Feedback:** Fixing inputs or choosing a different evaluator for a different goal are reasonable considerations, but changing mapping alone cannot provide missing evidence. The tutor supplied the solution: add policy text (refunds within 30 days) and map PolicyText to context; expected-answer agreement is a different goal. No subsequent independent mapping check was reported; the gap remains.

3. **Prompt:** 'Tutor example: a run has status completed, but its results show that 20 of 100 responses failed groundedness. Would you treat that as an execution problem or a detected quality problem? Is the status alone enough to approve deployment?'

   **Initial learner response:** 'It will depend on what your threshold is for groundedness. If it is within the threshold, then it might be approvable for deployment.'

   **Feedback:** Correct conditional gate reasoning. The tutor distinguished existing per-item failures from an aggregate release gate and noted that critical cases may block; completed means execution success only. The learner did not explicitly classify execution versus quality; no independent classification or follow-up is claimed.

4. **Prompt:** 'your release policy requires: At least 95% of responses to pass groundedness. No critical policy violations. The run completes, 98% pass, but one response contains a critical policy violation. Would you deploy, and why?'

   **Initial learner response:** 'No, because there is a requirement of "No critical policy violations"'.

   **Feedback:** Correct independent critical-gate decision: both requirements must hold, and a high average cannot override a hard gate. No follow-up reported.
