### Ordinary lesson checks

1. **Prompt:** “A colleague adds --all-traffic to that green creation command ‘so the deployment is ready to test.’ Would you keep or remove it, and why?” **Initial:** “If we want to have all the traffic go to green, then we keep it.” **Feedback:** Correct conditional meaning of the flag; remove it for the stated testing goal, since the candidate is directly testable without promotion. Partial scenario evidence; no independent retry.

2. **Prompt:** “Green’s creation operation finishes successfully, but its predictions have not been checked yet. You want to test it while blue continues serving all ordinary clients. What would you do next—describe the action rather than recalling exact syntax?” **Initial:** “either mirror-traffic or set partial traffice to green.” **Feedback:** Mirroring retains blue responses, but a partial live share exposes clients; the source sequence first directly tests a known sample. Tutor supplied direct-invoke code; no independent choice of that action demonstrated here.

3. **Prompt:** “Your test request explicitly targets green while blue has 100% live traffic. Who receives that test request, and does sending it change where ordinary client requests go?” **Initial:** “a named traffic will go to that endpoint/deployment.” **Feedback:** Yes, green deployment under the shared endpoint gets the request; ordinary routing is unchanged. The latter part was tutor-supplied, not explicitly learner-stated.

4. **Prompt:** “Green provisions successfully, but its scoring code expects a field named features, while your existing clients send data. Would increasing instance_count solve that problem? What would you investigate instead?” **Initial:** “no. instance_count is for capacity readiness. I will check either the scripts or the arguments.” **Feedback:** Correct capacity versus compatibility; inspect input parsing and actual request contract. Independent meaningful conceptual application.

5. **Prompt:** “After testing green, you want this JavaScript client to behave like an ordinary production client and follow the endpoint’s blue/green traffic allocation. What would you change in the request?” **Initial:** “I will be setting the --traffic to green=100 ”. **Feedback:** That promotes globally rather than making the request follow current policy; remove the targeting header. Tutor provided explanation and table.

6. **Scaffolded follow-up to 5:** “The endpoint is already blue 90% / green 10%. You want your JavaScript client to use that existing split without changing it. Would you update endpoint traffic, or remove the deployment-targeting header?” **Response:** “remove the targetting header”. **Feedback:** Correct: follows the current split. This is scaffolded recovery, not a replacement for the initial response.

7. **Prompt:** “Your team moves this rollout to a Kubernetes online endpoint and proposes ‘mirror 10% to green before promotion.’ What limitation would you flag, and what testing step could you use before exposing clients to green?” **Initial:** “Mirrored traffic is not supported in Kubernetes online endpoint. Try traffic routing instead, like 10%”. **Feedback:** Unsupported feature correctly identified; 10% live is a valid rollout but exposes clients. Directly target green while blue remains at 100% for pre-exposure testing. That correction was tutor-supplied; no retry.
