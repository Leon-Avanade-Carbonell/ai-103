**Check 1 prompt:** “Tutor illustration: A teammate opens a pull request changing train.py. The automated validation fails, but GitHub still allows the teammate to merge. What would you investigate or change to make passing validation a requirement for merging into main?”

**Initial learner answer, verbatim:** “I will have to create/update some branch protection rules to wait for Github actions to pass before being merged into my main branch”

**Feedback:** Correct; configure branch protection/ruleset for main requiring relevant Actions status checks to pass before merging. The workflow runs validation; the rule enforces the gate. Tutor elaborated that PRs and reviewer approvals may also be required. No retry or execution.

**Check 2 prompt/context:** “One remaining idea is keeping branches short-lived, even when the overall work takes weeks. Tutor illustration: You’re adding a new feature to a training pipeline. It needs three changes: 1. A helper function to calculate the feature. 2. Tests for that function. 3. A change that enables the feature during training. Rather than keeping one branch open for weeks, you could merge small, tested increments while leaving the new feature unused until it is ready. Why would that approach reduce integration risk compared with one long-lived branch?”

**Initial learner answer, verbatim:** “stale code and some code merge issues might happen with long-lived branch. Smaller commits and regular pulls from the main branch is advisable to reduce the code merge issues.”

**Feedback:** Yes, long-lived branches drift from main, increasing conflicts and delaying discovery of incompatibilities. Tutor refinement: small commits and regularly pulling main help, but frequent merging of small reviewed changes back into main is central; updating a branch alone does not integrate its changes for others. The prompt scaffolded the incremental-feature example. No follow-up learner answer after clarification; the refined merge-versus-pull distinction was not independently demonstrated.
