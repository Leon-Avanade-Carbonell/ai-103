## Topics discussed

Components run as child jobs in a dependency graph with sequential or parallel steps and potentially different compute targets. The `@pipeline` decorator builds a `PipelineJob`; component outputs wire internal dependencies, while the return dictionary exposes selected pipeline-level outputs. An `Input` of type `URI_FILE` can reference the versioned asset `azureml:data:1`. Building and printing a YAML representation does not save, submit or run the job: a local definition does not select local compute. Examples were illustrative, not run; no installed SDK version was verified. Real evaluation requires held-out data.

### Ordinary lesson checks — M05-U03

**1. Prompt:** “You have three components: Prepare produces cleaned data. Train consumes that cleaned data and produces a model. Evaluate consumes both the model and the cleaned data. Which steps must wait for which others, and can Train and Evaluate run in parallel? Why?”

**Actual initial response:** “Train waits for the Prepared Data, and Evaluate requires both. With this requirment, the answer is 'no'. It cannot run in parallel.”

**Feedback:** Correct independent application. Train waits for Prepare; Evaluate waits for Prepare and Train. The model dependency prevents Train and Evaluate from running in parallel.

**2. Prompt:** “Suppose you remove "trained_model" from the return dictionary, but leave this line unchanged: model=train.outputs.model. Can Evaluate still consume the model? What changes for someone using the overall pipeline’s outputs?”

**Actual initial response:** “yes. it will just not have the access to the trained model; just the report.”

**Feedback:** Correct distinction in the pipeline-level caller context: Evaluate still consumes the internally wired model, but the caller receives only the report as a named pipeline-level output. The tutor clarified that removing the return key does not delete the child-job artifact, which remains accessible through the child job.

**3. Prompt after input/print example:** “After these two calls, has Prepare actually run? What have we created instead?”

**Actual initial response:** “No. it does not run; but it will have the pipelines that can be used locally.”

**Feedback:** No execution is correct, but “locally” is ambiguous. A `PipelineJob` object was created locally, not configured local component execution. Build locally, submit to Azure ML, then execute on configured compute.

**4. Clarifying prompt:** “if you build and print this object on your laptop, does that make your laptop the compute target for Prepare and Train?”

**Actual initial response:** “yes”

**Feedback:** Incorrect. The laptop constructs the configuration; printing does not run it or select the laptop. On submission, steps execute on configured default or step-specific targets. Tutor used a work-order analogy and action table.

**5. Follow-up prompt:** “You build the pipeline object on your laptop, configure an Azure ML compute cluster for its steps, and submit it. Where do Prepare and Train run?”

**Actual follow-up response:** “In the AzureML”

**Feedback:** Correct: on the configured Azure ML compute cluster, not the laptop. This recovery followed explicit teaching and is scaffolded, not independent mastery evidence.
