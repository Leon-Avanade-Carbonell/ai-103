### [Q01 — On-demand trigger](../../lessons/01-mlops/06-automate-training-with-github-actions/quizzes.md#quiz-2026-11-13-session-04-q01)

Easy; single-answer; M06-U06; S1. **Prompt:** You want a team member to start a workflow on demand from the GitHub UI. Select one answer.

- A. schedule — Use a time-based trigger.
- B. workflow_dispatch — Use an on-demand workflow trigger.
- C. push — Use a branch-update trigger.
- D. repository_dispatch — Use an external repository event.

**Initial selection:** B. workflow_dispatch. **Key:** B. **Outcome:** correct. **Tutor explanation:** workflow_dispatch supports on-demand runs; schedule is time-based, push responds to commits, and repository_dispatch receives external API-generated events. **Follow-up:** none.

### [Q02 — Single-script job](../../lessons/01-mlops/06-automate-training-with-github-actions/quizzes.md#quiz-2026-11-13-session-04-q02)

Easy; single-answer; M06-U06; S1. **Prompt:** Training fits in one script, with no need to connect separate reusable components. Which Azure ML job type is the straightforward choice? Select one answer.

- A. Pipeline job — Submit a graph of connected components.
- B. GitHub Actions job — Run steps directly on a GitHub runner.
- C. Command job — Run a script on Azure ML compute.

**Initial selection:** C. Command job. **Key:** C. **Outcome:** correct. **Tutor explanation:** A command job suits a single-script Azure ML workload; a pipeline connects components, while a GitHub Actions job is not an Azure ML job type. **Follow-up:** none.

### [Q03 — Azure-event bridge](../../lessons/01-mlops/06-automate-training-with-github-actions/quizzes.md#quiz-2026-11-13-session-04-q03)

Medium; multiple-answer; M06-U06; S1. **Prompt:** New training data arrives in Azure Storage. You want this Azure-side event to start a GitHub workflow that submits training. Select TWO correct statements.

- A. Actions subscribes directly to Event Grid — Connect Event Grid directly to the workflow trigger.
- B. Use a Function or Logic App intermediary — Receive the Azure event and call GitHub.
- C. Use repository_dispatch at GitHub — Accept an external API-generated event.
- D. Use pull_request for the storage event — Treat the arrival of data as pull-request activity.

**Initial selections, returned order:** C. Use repository_dispatch at GitHub; D. Use pull_request for the storage event. **Key:** B, C. **Outcome:** incorrect. **Tutor explanation:** C was correctly selected, B was missing, and D was incorrectly selected. Actions does not natively subscribe to Event Grid; an intermediary receives the event, authenticates to GitHub and calls its API. Storage arrival is not pull-request activity. Bridge: Azure event → intermediary → GitHub API → workflow. **Follow-up:** tutor explanation only; no learner retry.

### [Q04 — Post-merge trigger](../../lessons/01-mlops/06-automate-training-with-github-actions/quizzes.md#quiz-2026-11-13-session-04-q04)

Medium; single-answer; M06-U06; S1. **Prompt:** Your repository requires reviewed changes before merging into main. Which trigger best fits training after those changes land on main? Select one answer.

- A. workflow_dispatch — Start each training run on demand.
- B. schedule — Start training at fixed times.
- C. pull_request — Start validation for proposed changes.
- D. push filtered to main — Start training when commits land on main.

**Initial selection:** C. pull_request. **Key:** D. **Outcome:** incorrect. **Tutor explanation:** A merge updates main and produces the push event for this scenario. pull_request normally validates proposed changes; manual and scheduled triggers do not directly match code landing. Other GitHub event configurations exist, but the standard source distinction is PR validation versus post-merge push training. **Follow-up:** tutor explanation only; no learner retry.

### [Q05 — Submission, execution, quality](../../lessons/01-mlops/06-automate-training-with-github-actions/quizzes.md#quiz-2026-11-13-session-04-q05)

Hard; multiple-answer; M06-U06; S1 and taught tutor clarification. **Prompt:** Azure ML accepts a pipeline submission. Later, every component completes without execution errors, but evaluation reports a metric below your acceptance threshold. Select TWO correct conclusions.

- A. Submission acceptance proved training had finished — Treat acceptance as completion evidence.
- B. The pipeline completed successfully as an execution — Its components finished without execution errors.
- C. Model quality is automatically acceptable — Treat successful evaluation execution as sufficient quality.
- D. The model fails the stated quality requirement — Its reported metric is below the acceptance threshold.

**Initial selections, returned order:** D. The model fails the stated quality requirement; A. Submission acceptance proved training had finished. **Key:** B, D. **Outcome:** incorrect. **Tutor explanation:** D was correctly selected, B was missing, and A was incorrectly selected. Completion without errors establishes execution success; the below-threshold metric fails quality acceptance. Submission acceptance precedes completion, and an evaluation can execute successfully yet report unacceptable quality. **Follow-up:** tutor explanation only; no learner retry.
